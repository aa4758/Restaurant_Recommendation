> 원칙(01 결정문 유지): **네이버 등 크롤링 금지.** 공식 API · 공공데이터 · 제휴 · 업주/사용자 입력만 사용.

## 1. 필요한 데이터 (데이터 사전)

### 1-1. 사용자가 제시한 항목
| 항목 | DB 위치 | 비고 |
|---|---|---|
| 음식점 이름 | `restaurants.name`, `branch` | 지점명 분리 |
| 메뉴·가격 | `menus(name, price, is_signature)` | 대표메뉴 표시 |
| 가격대 | `restaurants.price_band` | **대표메뉴 가격 중앙값으로 계산** (~1만/1~2만/2~4만/4만+). 없으면 NULL → "가격 미확인" |
| 장르 | `genre`(앱 필터용 10종+기타: 치킨·주점 포함), `genre_detail`(원본 소분류) | 원본 보존 → 매핑 규칙 바꿔도 재계산 가능 |
| 위치 | `lat`, `lng`, `address`(도로명), `address_jibun`, `floor` | WGS84 |
| 음주 가능 | `alcohol` (1/0/NULL=미확인) | 아래 1-3 "인허가 종류"로 법적 판별 가능 |
| 지도 앱 링크 | **저장 안 함, 응답 시 생성** | 카카오: `place.map.kakao.com/{kakao_place_id}`, 없으면 검색 링크 `map.kakao.com/?q=`, 네이버: `map.naver.com/p/search/{이름 주소}` |
| 운영 시간 | `opening_hours(weekday, open/close, break, last_order)` | 요일별 1행, 자정 넘김은 `25:30` |
| 운영 날짜(휴무) | `opening_hours`에 행 없는 요일 = 정기휴무, `holiday_note` = "매월 둘째 화요일" 등 | 임시휴무는 사용자 신고로 |

### 2-2. 솔직한 한계
- **메뉴·가격·영업시간은 전국 단위 공공데이터가 없다.** C·D·J·K·L을 합쳐도 초기 커버리지는 일부.
  → 앱에서 "정보 미확인" 표시 + "정보 알려주기" 버튼(기존 `report` API)으로 사용자 참여 유도.
- 음주 여부: 휴게음식점 → 불가(확정). 일반음식점 → 가능하나 실제 판매 여부는 모름 → 주점 업종·메뉴·사용자 태그로 보강.

### 2-3. 적재 파이프라인
```
raw 파일/API (data/raw/, git 제외)
  → 어댑터: 출처별 정규화 레코드
  → 동일 가게 매칭(엔티티 매칭): 이름 정규화(공백·지점명·(주) 제거) + 거리 50m 이내 + 주소 번지 일치
  → restaurants 에 upsert (출처별 외부 ID 컬럼으로 연결, 다른 출처가 채운 컬럼·리뷰 보존)
  → 보강: menus / opening_hours / restaurant_signals
  → 파생값 계산: price_band, 노포 태그, 폐업 제외
  → 점수 배치 계산 (3장) → API
```
- 뼈대: **A(좌표·장르) + B(영업상태·일반/휴게·개업일)**. A에만 있고 B에서 폐업이면 `status=closed`.
- 갱신 주기: A 분기, B 월(폐업 반영이 핵심), C·D·E·F 월, H 분기.

## 3. 별점 — 수집과 계산

### 3-1. 문제
기존 모델의 `base`(외부 평점)는 **합법적으로 대량 확보할 출처가 없다**(2-1 "쓸 수 없는 것"). 광고 리뷰 비율도 외부 리뷰 본문이 필요하다.
→ prior를 **합법적으로 가질 수 있는 공공 신호** 위주로 재구성하고, 자체 리뷰가 빨리 prior를 대체하게 한다.

### 3-2. 사전 점수(prior) v2.1 — ✅ 구현됨 (01 결정문 "점수 모델 v2" + "v2.1")
```
prior_raw = 0.30 * 업력      min(log1p(영업연수)/log1p(20), 1); 백년가게는 최소 30년 간주(이중 가점 없음)  # B, E
          + 0.25 * 업무추진비  min(log1p(방문수)/log1p(30), 1)                # H
          + 0.15 * 위생등급    매우우수 1 / 우수 0.7 / 좋음 0.4 / 없음 0       # F
          + 0.10 * 지정업소    모범·안심식당·원산지표시 우수 중 하나라도 1     # E, P
          + 0.20 * 외부 평판   max(가이드 점수, 제휴 평점 0~1), 둘 다 없으면 0.4  # M·N·O(·미슐랭 법무 후), L
          - 행정처분 감점       최근 3년 건당 0.05, 상한 0.15                  # F
          - 광고 감점           자체 리뷰의 체험단·협찬 표시 비율 (기존 식·하한 유지)
prior_star = strict_map(prior_raw)   # 시군구 단위 분위수 → 평균 2.5, 4.5 이상 상위 ~3% (기존 유지)
```
- 착한가격업소(D)는 점수 무관 → 분위기 태그 `가성비` 를 조회 시 합성 + 대표메뉴·가격 출처.
- 업력은 "오래 살아남음 = 손님이 계속 옴"이라는 약한 신호. 양도·명의변경 시 인허가일자 초기화 여부 ⚠️ 확인 필요.
- 신호가 거의 없는 가게(대다수 초기 상태)는 prior가 평균 근처에 몰림 → 앱에 **"근거 부족"** 표시 권장.
- 분위수 단위: **시군구**. "이 지역 상위 N%"와 일치하고, 전국 100만 건을 한 번에 정렬할 필요도 없음.

### 3-3. 자체 별점 수집
| 방법 | 내용 |
|---|---|
| 앱 리뷰 (구현됨) | 0.5 단위, 엄격 기준 안내(2.5 평범 / 3.5 재방문 / 4.5 일부러 찾아감), 태그 = 분위기 데이터 |
| **영수증 인증** (2차 핵심) | 영수증 사진 OCR → 상호·일자로 방문 확인 + **메뉴·가격 자동 수집**(메뉴 DB 공백을 메움). OCR: 온디바이스(ML Kit 등) 또는 유료 영수증 OCR API |
| 위치 근접 확인 | 리뷰 작성 시 가게 200m 이내면 중간 신뢰 |
| 조작 방지 | 기기 ID당 가게별 30일 1회, 요청 레이트리밋, 신규 가게 단기간 만점 몰림 탐지 (QA 이슈 #2) |

### 3-4. 최종 별점 v2 — 제안
```
w_i   = 인증가중(영수증 1.0 / 위치근접 0.7 / 미인증 0.4) × 시간가중(0.5^(경과년수/2))
s_i'  = s_i − 0.5 × (작성자 평균 − 2.5)      # 후한 사람 보정, 작성자 리뷰 5개 이상일 때만
final = (k·prior_star + Σ w_i·s_i') / (k + Σ w_i),  k = 20
```
- 기존 식과 같은 구조(k=20, 유효 리뷰 20개면 50:50). n 대신 **가중치 합**을 쓰는 것만 다름.
- 자체 리뷰에서 체험단·협찬 문구가 있으면 해당 리뷰 w 축소 + 광고 감점 신호로 사용.

### 3-5. 계산 방식 (성능)
현재는 요청마다 전체 가게 점수를 다시 계산한다(QA 이슈 #5). 전국 데이터에서는 불가능하므로:
- **`scores` 테이블 + 배치 계산**(적재 후·리뷰 작성 시 해당 시군구만 재계산)
- `/recommend` 는 좌표 범위(lat/lng 인덱스)로 반경 안 후보만 조회
→ **전국(또는 시도 단위) 데이터를 API DB에 적재하기 전에 반드시 먼저 구현.**
